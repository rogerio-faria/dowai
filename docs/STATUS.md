release gates are not inferred from scaffolding or documentation.

| `init` | PARTIAL | Creates project/workspace JSON and model/test/state directories without overwriting existing workspace config; remaining layout/bootstrap work is pending. |
| `validate` | PARTIAL | Validates project schema/version, model directory, static refs/cycles, source declarations, SQL template syntax, and the implemented config subset without requiring run-time variable values. |
| Automatic/manual `plan` | PARTIAL | Offline ordering and warnings; literal `ref()` / `env.depends_on()` only; no complete SQL/Python AST. CLI preflights SQL templates and relation resolution in planned order using ephemeral `--vars` and `def_var` values. |
| Safe SQL template renderer | PARTIAL | Rust API and CLI planning support bounded conditionals, `var()`/`def_var()`, static SQL macros, Jinja comments, strict/lenient undefined handling, and stable errors without value interpolation; SQL is discarded after validation. |
| Effective config | PARTIAL | Loads admin/user/workspace/project layers, reports field origins, and enforces documented administrative ceilings; profiles support literal or environment-referenced passwords and are excluded from effective output. Full config catalog and secret providers are not implemented. |
| Sessions and variables | PARTIAL | Concurrent writes conflict explicitly (`DOWAI_SESSION_CONFLICT`, exit 3) under the default `error` policy; `wait_process` serialises runs of the same session through an OS file lock with a timeout.  Per-user local SQLite store supports UUID sessions, TTL expiry, typed JSON snapshots, bounded writes, and explicit end; values are plaintext, Unix permissions are restricted, and Windows ACLs are inherited. SQL and Python-only run paths persist variables only after all planned models succeed. |
| Python SDK | PARTIAL | Typed package with tests, plus `DowaiClient`, which runs the `dowai` binary with `--json` for plan, run, retry, runs, run detail and logs. The CLI and the client share one code path; 7 parity tests compare both on the same project and journal (AC034). A failed run that started reports its `run_id` on either path, the same identifier the journal stores (ENT-015). `Env` is not bound to the engine. |
| PostgreSQL adapter | PARTIAL | TLS-by-default adapter supports bound parameters, password environment-variable references, and transactional table/view replacement. SQL models are restricted to one statement, with quoted strings, dollar-quoted bodies, and nested comments handled by the guard; destructive relation changes require explicit adapter approval. Adapter smoke tests pass against PostgreSQL 17.4 with loopback TLS disabled; remote TLS is not verified. |
| SQL execution | PARTIAL | `run` plans, renders, resolves `ref()` and declared `source()` relations, and executes table/view models on PostgreSQL, MySQL, Oracle or SQL Server selected by profile; external writes are opt-in, replacing existing relations requires confirmation by default, sources are not plan nodes, and variables persist only after all selected models succeed. SQL source reads use the selected execution profile and connection; a declared different profile is rejected when referenced, with no automatic cross-database copy or type conversion. `{{ run("other.sql") }}` reuses the SQL run profile. PostgreSQL replacement is transactional; MySQL replacement stages and swaps with `RENAME TABLE` (DDL is not transactional). Full refresh is implemented for PostgreSQL and MySQL and checks schema drift; Oracle and SQL Server reject it. PostgreSQL E2E exists; opt-in MySQL SQL same-profile and mismatched-profile E2E coverage has been added but was not run here because database test settings are unavailable. |
| Python subprocess runtime | PARTIAL | Mixed SQL/Python runs (topological or manual order) share session variables with Python and SQL: SQL `def_var` is visible to later Python nodes and Python `setVar` selects SQL branches of later models; variables are published only if the whole run succeeds (E2E in `mixed_sql_python_e2e.rs`). Declared sources (`env.source`) work in Python-only and mixed runs with PostgreSQL, MySQL, Oracle or SQL Server profiles; `env.source(name, table, profile=None)` can override the declared profile, otherwise using the declared or default execution profile (MySQL requires a primary key for ordered batches; its filters remain unsupported). Python-only plans run in a project-local venv through versioned bounded JSON IPC (NDJSON, one message per line), with a minimal inherited environment, timeout and process-tree termination on Windows (Job Objects) and Unix process groups (detached Unix children can escape), and `Env` variable/static-dependency operations. E2E covers successful ordering, variable persistence, model exception, unsupported operations/returns, malformed IPC, and timeout without committing staged values. Imperative `env.run("x.py")` from a Python model executes another Python model in a supervised child with inherited pending variables (merged back only on success), a recorded invocation tree (`RunResult.invocations`, `call_type` `static`/`imperative`/`dependency`), cycle and depth/invocation-count limits, the `env.manual()` context, and `DowaiExecutionError` with stable codes. `{{ run("x.py") }}` from SQL receives the SQL model as `origem`; Python can explicitly choose a write destination with `env.write()`. `env.run("x.sql")` executes the SQL model on the run's selected database profile and session, with its `ref()` predecessors first in automatic mode, recorded as `call_type` `imperative` with stable `DowaiExecutionError` codes (ENT-114). ENT-040: nested `env.run` returns an object with `run_id`, `invocation_id`, `status`, `failed`, `execution_mode` and `duration_ms` (the `run_id` is the parent run's); `env.plan(target, mode=None)` and `env.validate()` return the same JSON as `dowai plan --json` and `dowai validate --json` through the same engine functions (E2E `ac040_*`, and `env_plan_and_validate_match_the_cli_json_output` for CLI parity). `setVar`/`getVar` stay a local overlay, as before. Datasets: `env.ref(name)` supports PostgreSQL, Oracle and SQL Server model tables, but not MySQL model datasets; `env.source()` supports declared sources on all four adapters. `env.write` is implemented, see the External writes row. `env.connections.get` returns an opaque handle (ENT-043, `connections_e2e`). Cancellation and the run journal are implemented (see their rows). `to_*`, dependency installation/authorization, SDK binding, and sandboxing are not implemented. |
| External writes (`env.write`) | PARTIAL | Python `env.write(rows, target, table, mode, keys, confirm_replace)` writes to a `postgres`, `mysql`, `oracle` or `sqlserver` profile in one transaction per write session, atomic only inside the destination database. Modes: `append`, `replace` (requires `confirm_replace=True`), `upsert` (requires a unique index exactly on `keys`; PostgreSQL `ON CONFLICT`, MySQL `ON DUPLICATE KEY UPDATE`). Requires `security.allow_external_writes`. A PostgreSQL-to-MySQL transfer is two independent transactions. E2E: `write_pg_e2e`, `write_mysql_e2e` (opt-in). Incremental loads with a model-declared watermark kept in the session and published only after commit (ENT-066, `incremental_*` in `write_pg_e2e`). Direct library writes are detected by AST and can be denied with `security.deny_direct_library_writes` (ENT-049, `direct_library_write_is_refused_when_the_policy_denies_it`). |
| MySQL adapter | PARTIAL | Adapter in `src/dowai-databases/mysql` (ENT-034, D-115) validated against MySQL 8.0.46 on loopback with TLS disabled: 14 contract tests plus `write_mysql_e2e` and `mysql_source_e2e` (opt-in). Works as an SQL execution profile, an `env.write` destination, and an `env.source` origin. SQL materialization and same-profile source reads have opt-in E2E coverage; cross-profile SQL sources are rejected rather than staged. TLS against a remote server is not verified. |
| Oracle and SQL Server adapters | PARTIAL | SQL table/view models, nested SQL on the same connection, Python source reads and destination writes are integrated and tested against live encrypted servers. Source pagination requires a primary key; filters are unsupported and non-null values are text. Unkeyed model tables use Oracle ROWID or SQL Server binary-converted columns (not all types are convertible). Atomic full refresh is unavailable; Oracle DDL commits implicitly and table replacement is not atomic. Oracle cancellation can be delayed by the server, and its client timeout is per round trip. Interrupted SQL Server connections are discarded; commit or DDL outcomes may be uncertain. |
| Run journal | PARTIAL | Local SQLite journal (`runs.sqlite3`, schema version 2, owner-only permissions) records run and invocation status, timings, stable error codes, requested targets, profile, and variable count for every run outcome, including failures; `dowai runs list|show`, `dowai logs`, and `dowai retry` (B-05c) read it. Variable values, SQL, messages, and paths are not stored. No AUDIT stream. |
| Audit trail | PARTIAL | Separate append-only `audit.jsonl` (schema_version 1, owner-only permissions) receives run, node, variable-name, external-write, policy-denial and nested-invocation events with correlation IDs, UTC timestamps, engine version, and SHA-256 hashes of model, effective configuration, and plan. It is independent of log levels and cannot be disabled by project configuration. It is not immutable (no WORM or signing). Values, SQL, credentials, and absolute paths are never written. Not yet readable through the CLI. |
| Cancellation | PARTIAL | Ctrl+C/SIGTERM/SIGHUP (Unix) and Ctrl+C (Windows) cancel `dowai run` with status CANCELLED, exit 130 and `DOWAI_CANCELLED`. Python process trees are terminated; in-flight PostgreSQL statements are cancelled and rolled back; no variables are published. Tested with real SIGINT/SIGTERM on Unix and an in-flight `pg_sleep` against PostgreSQL 16.15. Not verified on Windows with a real signal. A commit completing before cancellation counts as succeeded. |
| Plugin host (`dowai plugins list\|info\|sync\|resolve\|run`) | PARTIAL | Manifests, typed stubs (ENT-055), single resolver (ENT-106) and subprocess execution with manifest timeout, AUDIT entry and idempotency key (ENT-107). `run` needs `python.interpreter` set to the project venv and an `--idempotency-key` when the manifest requires one. Tests: `plugin_execution`, `plugin_permissions`, `plugin_rest`, `plugin_email` (runtime) and `plugins_sync_cli_e2e` (CLI). |

## Verification

Linux (Ubuntu 24.04, x86_64, rustc 1.99.1 stable, 2026-11-10):
`cargo fmt --all -- --check`, `cargo check --workspace --all-targets --locked`,
and `cargo test --workspace --locked` pass with 119 tests passed and 3 opt-in
PostgreSQL tests ignored. Building on Linux with the system OpenSSL headers
requires `OPENSSL_DIR=/usr OPENSSL_LIB_DIR=/usr/lib/x86_64-linux-gnu
OPENSSL_INCLUDE_DIR=/usr/include` when `pkg-config` is absent. The Python SDK
suite has 11 passing `unittest` cases (`PYTHONPATH=src`). The opt-in PostgreSQL
adapter smoke tests and runtime E2E pass against a PostgreSQL 16.15 cluster
running on loopback (ephemeral, user-owned, TLS disabled, scram-sha-256). This does
not verify remote TLS, production credentials, or PostgreSQL 17. Windows and
hosted CI runs have not been executed from this workspace. No installer has been
verified. Evidence log: `_gestao/EVIDENCIAS.md` (management folder, not tracked by Git).

Latest full run (2026-11-13, commit f10c0fe and later): `cargo fmt --all -- --check`
and `cargo clippy --workspace --all-targets --locked -- -D warnings` pass, and
`cargo test --workspace --locked -- --include-ignored --test-threads=1` passes with
PostgreSQL 16.15 and MySQL 8.0.46 on loopback (TLS disabled): 626 passed, 0 failed.
The README quick start was run from an empty directory against a local
PostgreSQL 16 database (`dowai_demo`).

The opt-in PostgreSQL tests require a dedicated disposable database and these
environment variables: `DOWAI_TEST_PG_HOST`, `DOWAI_TEST_PG_PORT`,
`DOWAI_TEST_PG_USER`, `DOWAI_TEST_PG_DATABASE`, and
`DOWAI_TEST_PG_PASSWORD`. Set `DOWAI_TEST_PG_TLS=disabled` only for a loopback
test server that has no TLS configured. Run them with:

```powershell
cargo test -p dowai-postgres --test smoke -- --ignored --test-threads=1
cargo test -p dowai-runtime --test postgres_e2e -- --ignored --test-threads=1
```
